Phase 2 — Authentication
Concepts introduced while building authentication, session management, and protected routes.

============================================================================================================================================
Password hashing (bcrypt)

What is it?
A one-way cryptographic hashing function designed specifically for securely storing passwords.

What does it do?
It converts plain-text passwords into fixed-length cryptographic strings with random salts, preventing the original password from ever being decrypted.

Why do we need it?
Storing plain-text passwords in databases is a catastrophic security risk. If the database is compromised, user credentials remain protected.

What are its benefits?
Built-in unique salting per password, adjustable computational work factor to resist brute-force attacks, and constant-time string comparison.

What are the alternatives, if any?
Argon2, PBKDF2, or scrypt.

============================================================================================================================================
JWT access tokens and refresh tokens

What is it?
A dual-token strategy using digitally signed JSON Web Tokens (JWT) for stateless authentication and session management.

What does it do?
Provides short-lived access tokens (15 minutes) for API requests and long-lived refresh tokens (7 days) stored in the database for renewing sessions.

Why do we need it?
It balances security and user experience. Short-lived tokens minimize the exposure window if intercepted, while refresh tokens prevent users from having to re-authenticate constantly.

What are its benefits?
Stateless request authorization without hitting the database for every single API call, combined with server-side control via database-backed refresh tokens.

What are the alternatives, if any?
Stateful session IDs with server-side session stores (e.g. Redis/PostgreSQL on every request), or single long-lived access tokens.

============================================================================================================================================
Refresh token rotation & reuse detection

What is it?
A security mechanism where refresh tokens are single-use, and issuing a new access token invalidates the old refresh token and produces a new one.

What does it do?
Every time a refresh token is exchanged, it is revoked in the database and replaced. If a previously revoked token is submitted again, the system detects a token reuse attack and revokes all active sessions for that user family.

Why do we need it?
To detect and neutralize token theft. If a malicious actor intercepts a refresh token, any attempt by either the legitimate user or the attacker to reuse an invalidated token triggers automatic session invalidation.

What are its benefits?
Immediate detection of session hijacking, automatic containment of compromised accounts, and protection against stolen credential replay.

What are the alternatives, if any?
Static, non-rotating refresh tokens (less secure against token theft); sliding window sessions without revocation tracking.

============================================================================================================================================
Authentication middleware (Bearer token verification)

What is it?
An Express middleware function that intercepts incoming HTTP requests to verify the caller's identity before allowing access to protected route handlers.

What does it do?
It inspects the HTTP `Authorization` header, parses the `Bearer <token>` format, cryptographically verifies the JWT signature and expiration, and attaches the decoded user payload to `req.user`.

Why do we need it?
Protected API endpoints must reject unauthorized, tampered, or expired requests while ensuring route handlers have immediate access to the authenticated user's identity.

What are its benefits?
Centralized security enforcement, reusable across all protected routes, prevents code duplication, and keeps public routes (like `/health` or `/login`) easily distinguishable from protected routes.

What are the alternatives, if any?
Verifying tokens individually inside each route controller (redundant and prone to omission), or session cookies with cookie-parsing middleware.

============================================================================================================================================
Protected /me endpoint

What is it?
A protected API endpoint (`GET /api/v1/auth/me`) that returns the profile data of the currently authenticated user.

What does it do?
Using the user identity attached by the authentication middleware (`req.user`), it retrieves and returns safe user profile information (omitting password hashes) from PostgreSQL.

Why do we need it?
Client applications need a reliable way to fetch the active user's state on page load or token refresh to render the UI, display user details, and check permissions.

What are its benefits?
Standardized user profile endpoint, verifies user account status (`ACTIVE`), and serves as the baseline test for protected API routes.

What are the alternatives, if any?
Extracting user details only from the decoded JWT on the client side (can become stale if the user's role or status changes in the database).


============================================================================================================================================
Session invalidation and user logout

What is it?
A mechanism to explicitly terminate an authenticated user session by revoking the refresh token in PostgreSQL.

What does it do?
When a user logs out (`POST /api/v1/auth/logout`), the server marks the refresh token's `revokedAt` timestamp in the database, preventing it from ever being used again to issue new access tokens.

Why do we need it?
Stateless access tokens cannot be easily invalidated before their natural expiry (15 minutes). Revoking the underlying refresh token ensures that once logged out, no further access tokens can be minted for that session.

What are its benefits?
Instant session revocation on the server side, idempotent and safe execution, clean cleanup for frontend clients, and foundation for "logout from all devices".

What are the alternatives, if any?
Client-side only token deletion (unsafe if token was intercepted); server-side blocklisting of all active JWT access tokens in Redis (heavier operational complexity than needed for MVP).

============================================================================================================================================
One-time password reset token & hashed persistence

What is it?
A secure mechanism to allow users who forgot their credentials to set a new password using a time-limited, single-use token.

What does it do?
Generates a cryptographically random plain token for the user, but stores only its cryptographic SHA-256 hash in PostgreSQL with a 1-hour expiration timestamp. When submitted, the token is verified, marked as used (`usedAt = NOW()`), and the user's password is updated with bcrypt.

Why do we need it?
If plain reset tokens were stored in the database and the database leaked, an attacker could immediately reset any user's password. Hashing the token protects accounts even in the event of a database compromise.

What are its benefits?
Zero plain-text token storage, single-use enforcement preventing token replay, short expiration window, and automatic session revocation upon password change.

What are the alternatives, if any?
Storing plain tokens in the database (insecure); short-lived signed JWT reset tokens (stateless, but harder to revoke immediately after one use without a blacklist).

============================================================================================================================================
User enumeration defense (Generic recovery responses)

What is it?
An authentication security practice where endpoints return the identical response message regardless of whether an account exists.

What does it do?
`POST /api/v1/auth/forgot-password` returns `200 OK` with "If an account with that email exists, password reset instructions have been sent" whether the email exists in PostgreSQL or not.

Why do we need it?
If the API returned `404 User Not Found`, malicious actors could automate requests to discover which email addresses belong to registered employees or admins in the system.

What are its benefits?
Prevents attacker reconnaissance and user profiling while preserving a clear and friendly user experience for legitimate users.

What are the alternatives, if any?
Explicit error messages like "Email does not exist" (creates severe email enumeration vulnerabilities).
